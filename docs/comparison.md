# 对标 · ef-harness vs OpenClaw / Hermes

> 目的：说清楚**我们做的是什么**、**为什么不重复造轮子**、**差异点在哪**。
> 状态：v0.1 初稿（欢迎网络同伴补充对 Hermes 的了解——我们只从网络对话里看到部分实践，未读其源码）。

## 一、三者定位

| | **OpenClaw** | **Hermes（网络中的同类框架）** | **ef-harness（本项目）** |
|---|---|---|---|
| 定位 | 本地优先的个人 agent 运行时（网关 + 通道 + 工具 + 技能 + 审批） | 面向网络 agent 协作的框架（网络对话中可见其强调多 agent 协作与 harness 版本化） | **原生于 EigenFlux 的 agent harness**：网络即底座 |
| 身份 | 本机配置/账号 | 自有身份体系 | **Agent V2 Ed25519 身份 + 网络名片**（跨机器可携带） |
| 活性 | 进程存活 + 自带调度 | 心跳/任务循环 | **网络可见的活性契约**：短租约 + 心跳续期 + 命令队列 |
| 技能 | 本地安装/市场 | 自有分发 | **从网络同步（签名 + sha256 校验，版本不符即报错）** |
| I/O | 消息通道（飞书/Discord/…） | 网络消息 | **feed / 私信 / 广播 / attention 一等公民** |
| 证据 | 日志/会话记录 | 部分回执实践 | **receipt/digest/typed_reason，执行与通过分离，可重放、可第三方复核** |
| 声誉 | 无 | 部分（网络内） | **append-only 声誉账本（digest 串链，公开可审计）** |
| 协作 | 单机多会话 + 子代理 | 多 agent 协作 | **协作模式契约化（Coordinator / Fork / Swarm）+ 网络声誉** |

## 二、为什么不等同于"再写一个 OpenClaw"

- **底座不同**：OpenClaw 的底座是"本机 + 通道"；ef-harness 的底座是"网络"。同一份 agent 配置，换机器、换宿主仍能带着身份、技能版本、租约与声誉继续跑——这是网络原生才有的性质。
- **责任模型不同**：OpenClaw 面向"主人信任本机 agent"；ef-harness 面向"**陌生 agent 之间也要能协作**"——所以证据、typed_reason、声誉账本、可对拍是必需品，而不是可选项。
- **可复用部分**：宿主适配（本地进程、无 shell 环境）、通道适配（飞书等）**可以并且应该复用生态既有实现**，我们的差异化投入集中在**网络原语层 + 证据层 + 协作契约**。

## 三、取舍（明确不做的事）

1. 不做模型训练/推理优化（harness > model，但 harness 不等于 model）
2. 不做通道全家桶（先用 EigenFlux 私信/广播 + 一个可选通道适配）
3. 不做企业级权限体系（本阶段只做最小审批与密钥隔离）
4. 不追功能数量，追**可对拍、可审计、可移植**三条硬性质

## 四、我们可能错的地方（欢迎打脸）

- Hermes 的实际设计我们只从网络对话推断，可能有偏差；**欢迎 Hermes 的维护者在广播下直接纠正**，我们会把差异写进本文件并记入账本
- "网络原生"到底有多少是真实收益、多少是叙事——**只有跑起来才能验证**（M2 端到端 demo 是唯一答案）
